## 결론: 기존 평가함수가 이미 견고

**왜 추가 항이 개선을 못 내는가:**
1. **신호 중복**: 처치 임박/덱아웃은 이미 기존 라이프/오라 선형 항에 간접 반영됨.
   처치하면 상대 라이프→0으로 WIN이 뜨므로 이미 최고점. 새 항은 중복 신호.
2. **간격 제어는 _attacks_in_range와 중복**.
3. **가중치는 이미 잘 튜닝됨**: 초기 설정(W_LIFE=10, W_AURA=2, ...)에서
   벗어나면 오히려 하락. 세션 초반 값이 견고.

**HeuristicBot의 진짜 약점**은 "상대 대응 무시"(낙관적 1수 탐색)이지만,
이를 고치려면 상대 반응 모델링 = 2수 앞 탐색이 필요한데, 이는 이미 실패
(가변 턴 구조와 불일치, session_uct_improvement.md 참조).

## 최종 판단
- 평가함수 고도화 항은 보존하되 **기본 OFF** (USE_ADVANCED_EVAL=False).
  중립이라 계산비용만 추가하므로 끔. 연구·재현용으로 코드는 유지.
- 기존 evaluate()가 이 게임에서 실질적 최적선. 챔피언 MonteCarloBot(K=48) 유지.

## 세션 전체 교훈 (UCT + 평가함수)
두 번의 "개선 시도"가 모두 음성 결과였지만, 이는 **초기 설계(평가함수 + MC
하이브리드)가 예상보다 훨씬 견고했다**는 강력한 증거다. 막연한 백로그
("UCT 개선", "평가함수 고도화")를 실측으로 닫고, 추가 투자가 무의미함을
확정한 것이 성과. 더 큰 개선은 알고리즘/평가 미세조정이 아니라 근본적으로
다른 접근(신경망 평가 학습 등, 대량 self-play 필요)에서만 가능할 것.
